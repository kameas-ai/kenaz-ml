# WP01 — Feature Definitions

## Objective

Author the Feast entities, feature views, and feature services that ship inside the open-source package and act as the single definition consulted by both deployments.

## Context

Feature definitions today are Python functions with no registry, no lineage, and no versioning. This package makes them declared artifacts.

**Feast does not compute anything here** (D-002). `sigil_ml.features` remains the arithmetic. These definitions declare *what exists* — entity, fields, types, ordering, TTL — so both deployments and the registry agree on the shape.

Read first: [data-model.md](../data-model.md) §Entities and §Feature views, [research.md](../research.md) D-002.

## Subtasks

### T001 — Entities

**Purpose**: The join keys features are grouped by.

**Steps**:

1. Create `src/sigil_ml/feature_store/__init__.py` and `definitions.py`.
2. Declare three entities: `task` (join key `task_id`), `node` (`node_id`), `tenant` (`tenant_id`).
3. `tenant` is cloud-only. It may be declared here but must not appear in any feature view the local registry needs — the local deployment is single-user and has no tenant concept.
4. Join keys must match the column names already used in the `tasks` and `events` tables. Do not invent new names.

**Files**: `src/sigil_ml/feature_store/__init__.py`, `src/sigil_ml/feature_store/definitions.py`

**Validation**:
- [ ] Three entities declared with correct join keys
- [ ] Join keys match existing table columns
- [ ] `tenant` not required by any locally-resolvable feature view

### T002 — Feature views mirroring `FEATURE_NAMES` exactly

**Purpose**: FR-001 and FR-002. This is the subtask where a mistake is most expensive.

**Steps**:

1. Declare one feature view per model family: `stuck_features`, `duration_features`, `workflow_features`, `activity_features`, and the `fleet_*` views.
2. **Field order must be identical to the corresponding `FEATURE_NAMES` constant.** Import the constants from `src/sigil_ml/models/stuck.py` (6 features), `models/duration.py` (4), and the others, and derive the field lists from them rather than retyping the names. Both trainers build vectors as `[features[f] for f in FEATURE_NAMES]` — positionally — so a divergence here silently permutes every model input with no error.
3. Types are `Float64` throughout, matching what the extractors return.
4. Give each view a TTL bounding how far back a point-in-time lookup will reach. State the chosen value and the reasoning in a comment; do not leave it implicit.
5. Sources differ by deployment and are wired in WP02/WP04 — declare the view shape here without hard-coding a cloud-only source into the shipped definitions.

**Files**: `src/sigil_ml/feature_store/definitions.py`

**Validation**:
- [ ] One view per model family
- [ ] Field lists **derived from** `FEATURE_NAMES`, not retyped
- [ ] Ordering identical to the constants
- [ ] TTL set with a documented rationale
- [ ] No cloud-only source baked into a shipped definition

### T003 — Feature services

**Purpose**: FR-010 — the versioned contract naming exactly what one model consumes.

**Steps**:

1. Declare a `FeatureService` per model, naming that model's feature view.
2. Name them so the mapping to model names is unambiguous — the model names Go queries (`stuck`, `suggest`, `duration`, `quality`, `profile`) are fixed by `CLAUDE.md` and must not be renamed here.
3. A training run records which service it consumed; keep names stable, since changing one changes that record's meaning.

**Files**: `src/sigil_ml/feature_store/definitions.py`

**Validation**:
- [ ] One service per model
- [ ] Names map unambiguously to model names
- [ ] No existing model name changed

### T004 — Definition-vs-constant conformance tests

**Purpose**: Prove T002's central claim mechanically, so it cannot rot.

**Steps**:

1. Create `tests/test_feature_store_defs.py`.
2. For each feature view, assert its ordered field-name list **equals** the corresponding `FEATURE_NAMES` list. Use ordered comparison — a set comparison would pass on a reordering, which is the exact failure this guards.
3. Assert counts explicitly: stuck 6, duration 4.
4. Assert every declared field is `Float64`.
5. Assert each feature service references an existing view and that every model name has exactly one service.
6. Add a test that fails loudly if a new `FEATURE_NAMES` constant appears with no corresponding feature view — otherwise a future model silently ships unregistered.

**Files**: `tests/test_feature_store_defs.py`

**Validation**:
- [ ] Ordered comparison, not set comparison
- [ ] Counts asserted
- [ ] Types asserted
- [ ] Services map one-to-one with models
- [ ] New-constant-without-view case covered

## Risks

| Risk | Mitigation |
|---|---|
| Field ordering diverges from `FEATURE_NAMES` | Derive from the constants; T004 asserts ordered equality |
| Definitions drift as a second source of truth | Import the constants rather than retyping names |
| A future model ships unregistered | T004 covers the new-constant-without-view case |
| Computation creeps into definitions | Explicitly prohibited by D-002; reviewer checks |

## Reviewer Guidance

1. **Check the field lists are derived, not retyped.** A literal list of feature names in this file is a second source of truth and should be rejected.
2. **Confirm the conformance test compares ordered lists.**
3. **Look for any arithmetic** — there should be none.
4. **Confirm no cloud-only source** is baked into a definition that ships to open-source users.
