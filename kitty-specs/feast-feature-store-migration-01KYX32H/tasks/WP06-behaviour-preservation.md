# WP06 — Behaviour-Preservation Regression

## Objective

Prove the migration changed no feature value, in either deployment.

## Context

This is a **behaviour-preserving** migration (C-005). Feature names, ordering, and computed values are identical before and after; only registration, storage, and retrieval move. That claim is easy to state and easy to violate quietly — a rewiring that drops a key, reorders a vector, or rounds a float would pass every other package's tests while corrupting every model that consumes it.

The models index vectors positionally against `FEATURE_NAMES`, so a reordering produces no error at all — just silently wrong predictions.

Read first: [spec.md](../spec.md) C-005 and User Story 6, [quickstart.md](../quickstart.md) §3.

## Subtasks

### T023 — Pre-migration baseline capture

**Purpose**: Something to compare against. **Order-sensitive** — baselines taken after the migration prove nothing.

**Steps**:

1. Derive baselines from the **pre-migration** commit. Check out the merge-base, run the extractors against fixed fixtures under a pinned clock and pinned timezone, and record the output.
2. Commit them as **literal values**, not runtime computations:

```python
# Captured from pre-migration <sha>, fixture TASK_A, clock pinned to NOW_MS, TZ=UTC.
PRE_MIGRATION_STUCK_TASK_A = {
    "test_failure_count": 5.0,
    "time_in_phase_sec": 1800.0,
    ...
}
```

3. Comment each block with its provenance — commit, fixture, clock, timezone. A reader must be able to tell these are recorded observations rather than expectations someone typed.
4. **Pin the timezone.** `time_of_day_hour` derives from `time.localtime()`, so duration baselines are only reproducible under a fixed TZ. The sibling mission found this the hard way.
5. Cover every model family, plus the missing-entity and empty-input cases.

**Files**: `tests/test_migration_regression.py`

**Validation**:
- [ ] Baselines derived from the pre-migration commit
- [ ] Committed as literals, not computed at test time
- [ ] Provenance documented — commit, fixture, clock, TZ
- [ ] Timezone pinned
- [ ] All model families covered

### T024 — Value-equality regression tests

**Purpose**: SC-006 and C-005.

**Steps**:

1. With the clock and timezone pinned to the baseline conditions, resolve features through the **new** path and assert equality against the recorded literals.
2. Assert **ordered key lists**, not just dictionary equality — dict comparison in Python ignores insertion order, so it would pass on a reordering that breaks positional indexing.

```python
assert list(v.keys()) == stuck_model.FEATURE_NAMES
```

3. Assert exact float equality where the pre-migration values were exact. Do not silently loosen to approximate comparison to make a test pass — a value that moved is a finding, not a tolerance problem.
4. Cover both the local resolver path and the cloud retrieval path.
5. Cover missing entities and empty inputs — the degenerate cases where a rewiring most easily changes a default.

**Files**: `tests/test_migration_regression.py`

**Validation**:
- [ ] Equality against literals under pinned clock and TZ
- [ ] Ordered key lists asserted separately from value equality
- [ ] Exact comparison retained where it was exact
- [ ] Both deployments covered
- [ ] Degenerate cases covered

### T025 — Cross-deployment agreement tests

**Purpose**: FR-015 and SC-005.

**Steps**:

1. Feed identical task and event data through the local path and the cloud path; assert the resulting vectors are identical, key order included.
2. Use the same reference time for both, so any divergence is attributable to the deployment rather than to timing.
3. Assert against the same baselines from T023 — both deployments should match the pre-migration values, which also proves they match each other.
4. Cover at least the stuck and duration families; extend to fleet models if fixtures allow.
5. If the cloud path needs Postgres, use the existing test approach for cloud paths rather than inventing a new harness.

**Files**: `tests/test_migration_regression.py`

**Validation**:
- [ ] Identical vectors across deployments, ordering included
- [ ] Same reference time used for both
- [ ] Both compared to the T023 baselines
- [ ] Stuck and duration covered at minimum

## Risks

| Risk | Mitigation |
|---|---|
| Baselines captured post-migration, proving nothing | T023 requires derivation from the pre-migration commit, with provenance in comments |
| Reordering passes because dict equality ignores order | T024 asserts ordered key lists separately |
| A drifted value gets papered over with `approx` | T024 requires exact comparison where it was exact; a moved value is a finding |
| Timezone-dependent values irreproducible | T023 pins TZ |

## Reviewer Guidance

1. **Verify baseline provenance from the comments and from git history.** If the numbers could have come from post-migration code, this package has no value.
2. **Check ordered key assertions exist** separately from value equality.
3. **Look for `pytest.approx` on values that were previously exact** — that is a drifted value being hidden.
4. If any value legitimately had to change, it belongs in the spec as an amendment, not absorbed into a tolerance here.
