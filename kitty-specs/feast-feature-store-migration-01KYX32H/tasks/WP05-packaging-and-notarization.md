# WP05 — Packaging and Notarization

## Objective

The frozen binary builds with Feast included, notarizes with every bundled native library signed and stapled, ships a read-only registry, and serves real feature calls on a clean machine.

## Context

**This is the highest-risk package in the mission.** Measured: Feast adds **+309 MB and +338 native libraries** to the bundle. Every one must be signed and stapled for macOS notarization. If this fails, the migration cannot reach open-source users at all — the logic packages are worthless without it.

Two failure modes deserve specific attention:

- **Dynamic imports.** Feast resolves providers and online/offline store implementations *by name at runtime*. PyInstaller's static analysis cannot follow that, so the expected failure is a binary that builds cleanly, starts cleanly, and dies on the first actual feature call. Testing startup proves nothing here.
- **Read-only application directory.** The bundle is signed; writing into it is both impossible and a signature violation. The registry ships inside it (D-001) and must never be written at runtime.

There is also a pre-existing hazard: **CI's `build` job is currently flaky**, failing on 6 of the last 7 runs on `main` for reasons unrelated to this work — `ci.yml` starts the server and waits a fixed `sleep 3` before curling it, which races startup. Fix or account for that before trusting a green result from this package.

Read first: [research.md](../research.md) D-001 and D-005, [spec.md](../spec.md) User Story 4, and the existing `freeze/kameas-ml.spec`.

## Subtasks

### T019 — Build-time `feast apply`, ship registry read-only

**Purpose**: FR-013 and D-001.

**Steps**:

1. Add a build step that runs `feast apply` against the shipped definitions and produces the registry artifact.
2. Bundle the resulting registry into the frozen binary so it is part of the signed artifact and inherits notarization's integrity guarantee.
3. **`feast apply` must not run at first launch.** The application directory is read-only, so a runtime apply would fail — and would put the definitions outside the signature.
4. Make the build fail loudly if apply fails. A binary shipping without a registry would fail at first feature call, on a user's machine.
5. Record the Feast version that produced the registry (D-007), so FR-016's mismatch diagnostic has something to compare against.

**Files**: `freeze/kameas-ml.spec`, build tooling

**Validation**:
- [ ] Registry produced at build time and bundled
- [ ] No runtime `feast apply` path exists
- [ ] Build fails loudly if apply fails
- [ ] Producing Feast version recorded

### T020 — PyInstaller hidden imports and binaries

**Purpose**: FR-011. Where the build actually breaks.

**Steps**:

1. Extend the existing `collect_submodules` pattern already used for `sklearn`, `scipy`, `numpy`, and `joblib` — same mechanism, so reviewers recognise it.
2. Add `collect_submodules("feast")` plus explicit `hiddenimports` for the providers and store implementations Feast loads **by name**: the local provider, the SQLite online store, and the Postgres online/offline stores if the cloud path is bundled. Static analysis will not find these.
3. Collect `pyarrow` and `grpcio` binaries and data files — both carry native extensions that `collect_submodules` alone will not bring.
4. Collect Feast's package data (templates, schemas) if it loads any at runtime.
5. **Verify by exercising a real feature call in the frozen binary**, not by a successful build. A clean build here means very little.
6. Keep additions grouped and commented so the next person can tell which entries exist for dynamic-import reasons.

**Files**: `freeze/kameas-ml.spec`

**Validation**:
- [ ] Feast submodules collected
- [ ] Dynamic providers and stores named explicitly
- [ ] `pyarrow` and `grpcio` binaries collected
- [ ] A real feature call succeeds in the frozen binary
- [ ] Additions commented with rationale

### T021 — Read-only application-directory verification

**Purpose**: FR-013, asserted rather than assumed.

**Steps**:

1. Run the frozen binary with its application directory mounted or chmod'd read-only, and exercise the full local flow: load config, read registry, resolve features, serve a prediction.
2. Assert no write is attempted inside the bundle. The online store must land in the user data directory, never beside the binary.
3. Cover first run with no existing online store — it must be created in the writable location without touching the bundle.
4. Add this as an automated check, not a manual procedure, so it cannot silently regress.

**Files**: `tests/test_frozen_smoke.py`

**Validation**:
- [ ] Full flow succeeds with a read-only app directory
- [ ] No write attempted inside the bundle
- [ ] Online store created in the user data directory
- [ ] Automated, not manual

### T022 — Notarization and bundle-size gates in CI

**Purpose**: FR-012, NFR-001, NFR-003, NFR-005.

**Steps**:

1. Add notarization verification to the release workflow: `codesign --verify --deep --strict` and `xcrun stapler validate` against the built bundle.
2. Add a bundle-size gate failing if growth exceeds NFR-001's 350 MB ceiling. Print the actual delta on every build so drift is visible before it breaches.
3. Measure cold start on the frozen binary against NFR-003's 10-second budget. `import feast` pulls `pyarrow` and `grpcio`, so measure the **real binary**, not a source checkout.
4. **Fix the pre-existing smoke-test race** while here: replace the fixed `sleep 3` at `ci.yml` lines ~103 and ~180 with a bounded retry loop. Leaving it means this package's result cannot be trusted either way. If you would rather not widen scope, say so explicitly in the completion notes rather than silently accepting a flaky gate.
5. Ensure the notarization check is not itself flaky — a gate that fails randomly gets ignored, which is worse than no gate.

**Files**: `.github/workflows/ci.yml`

**Validation**:
- [ ] Notarization verified in CI
- [ ] Bundle-size gate with the delta printed
- [ ] Cold start measured on the real binary
- [ ] Smoke-test race fixed, or its non-fixing explicitly recorded
- [ ] Gates are deterministic

## Risks

| Risk | Mitigation |
|---|---|
| Dynamic imports missing — builds clean, dies on first feature call | T020 requires exercising a real feature call, not startup |
| Notarization fails on 338 new native libraries | T022 verifies in CI on every release build |
| Something writes inside the signed bundle | T021 asserts under a read-only app directory |
| Bundle grows unnoticed past the accepted budget | T022 prints the delta and gates on it |
| Trusting a green CI that is already flaky | T022 fixes the `sleep 3` race, or records why not |

## Reviewer Guidance

1. **Do not accept "the build succeeded" as evidence.** Confirm a real feature call was exercised in the frozen artifact on a clean machine.
2. **Check the read-only test is automated** and actually makes the directory read-only.
3. **Look at the printed bundle delta** — it should be near the measured +309 MB. Materially more means something unintended was collected.
4. **Confirm the smoke-test race was addressed** or its deferral explicitly recorded.
