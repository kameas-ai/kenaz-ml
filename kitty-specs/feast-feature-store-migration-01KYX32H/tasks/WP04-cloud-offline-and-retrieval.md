# WP04 — Cloud Offline Store and Training Retrieval

## Objective

Build the half the previous attempt skipped: a real offline store holding feature values stamped with the event time they describe, and point-in-time-correct training retrieval over it.

## Context

The April branch declared `PushSource` feature views whose required `batch_source` pointed at parquet files that never existed — its own docstring says so, "because sigil-ml never runs offline batch materialization." With no offline half, Feast had nothing to do but cache, and the branch stalled.

This is where Feast earns its place. Training sets stop being a replay of extractors over history and become a retrieval of stored values as of each example's own moment.

**One property carries the whole package**: `event_timestamp` must hold the moment the values *describe* — the `as_of_ms` reference time from `feature-extraction-correctness` — never the time the row was written. Store the write time and every point-in-time guarantee becomes silently false while the API keeps returning rows.

Read first: [data-model.md](../data-model.md) §Offline store and §Training retrieval, [research.md](../research.md) D-006.

### T013 — `ml_features` table and schema

**Purpose**: The offline store.

**Steps**:

1. Create the table per [data-model.md](../data-model.md) §Offline store: `entity_type`, `entity_id`, `feature_view`, `event_timestamp`, `created_at`, `feature_values` (JSONB), with the composite primary key and the point-in-time index.
2. Python-owned. **No change to Go-owned tables** (C-004) — this is additive.
3. `event_timestamp` is `NOT NULL`. A row without one is unusable for retrieval and must be impossible to write.
4. `created_at` is for auditing only. Document in a comment that it must never be used for retrieval ordering — that mistake reproduces the exact bug `feature-extraction-correctness` fixed.

**Files**: `src/sigil_ml/feature_store/materialize.py` (DDL or migration alongside it)

### T014 — Materialization writing `event_timestamp`

**Purpose**: FR-009. The load-bearing subtask.

**Steps**:

1. Compute vectors using the existing extractors with a **per-example reference time** — `_reference_time_for(task)` already exists in `training/trainer.py` and resolves `completed_at → last_active → skip`. Import it; do not reimplement.
2. Write each row with `event_timestamp` set to **that reference time**, and `created_at` to now.
3. Tasks with no resolvable reference time are skipped, matching the training path. Log the skip count once, not per row.
4. Materialization runs as a scheduled or triggered job — never synchronously inside a training run.
5. Preserve tenant scoping; this is orthogonal to tenancy.

**Files**: `src/sigil_ml/feature_store/materialize.py`

**Validation**:
- [ ] `event_timestamp` = the example's reference time, never `now`
- [ ] `_reference_time_for` imported, not duplicated
- [ ] Unresolvable rows skipped; count logged once
- [ ] Not invoked synchronously from training
- [ ] Tenant scoping preserved

### T016 — Materialization tests

**Purpose**: Prove FR-009 before anything depends on it.

**Steps**:

1. Create `tests/test_feature_store_cloud.py`.
2. Assert `event_timestamp` equals the task's reference time — and, critically, **differs from `created_at`** when materializing a historical task. If they always match, nothing proves the correct value was stored.
3. Materialize under a frozen clock advanced far past the fixtures, so a write-time regression is obvious at a glance.

5. Assert values equal what the extractor produces directly — materialization must not transform.

### T017 — Cloud training via point-in-time retrieval

**Purpose**: FR-007 and FR-010 — replace replay with retrieval.

**Steps**:

1. In `cloud_trainer.py`, build an entity dataframe of `task_id`, `event_timestamp`, and label — one row per example — and retrieve features via the feature service.

### T018 — Point-in-time and leakage tests

**Purpose**: FR-008. The correctness proof.

**Steps**:

1. **The leakage test**: write two values for one entity at different event timestamps, retrieve as of the earlier one, and assert the later value does **not** appear.

```python
materialize(task="t1", event_timestamp=T0,          values={"edit_velocity": 1.0})
materialize(task="t1", event_timestamp=T0+3_600_000, values={"edit_velocity": 9.0})
row = retrieve(task="t1", as_of=T0 + 60_000)
assert row["edit_velocity"] == 1.0        # not 9.0
```

2. Assert rows with different timestamps receive different values — a single shared value across rows would indicate the as-of join is not happening.
3. Assert TTL bounds retrieval: a value older than the view's TTL is not returned.
4. Assert retrieved values equal what direct extraction at that reference time produces — closing the loop between the two paths.
5. Cover the empty-offline-store case.

**Files**: `tests/test_feature_store_cloud.py`

**Validation**:
- [ ] Leakage test present and passing
- [ ] Per-row value divergence asserted
- [ ] TTL boundary covered
- [ ] Retrieval matches direct extraction
- [ ] Empty store covered

## Risks

| Risk | Mitigation |
|---|---|
| `event_timestamp` set to write time — silently breaks every guarantee | T016 asserts it differs from `created_at` for historical tasks |
| Placeholder sources reproduce the April failure | T015 prohibits them explicitly |
| Partial retrieval trains a quietly worse model | T017 requires loud failure |
| The as-of join is not actually happening | T018 asserts per-row divergence, not just absence of error |

## Reviewer Guidance

1. **Check `event_timestamp` at the write site.** If it can ever be `now()` for a historical task, stop there.
2. **Run the leakage test.** It is the reason this package exists.
3. **Grep for placeholder or non-existent source paths** — the failure mode this mission was written to avoid.
4. **Confirm `_reference_time_for` is imported**, not reimplemented.
